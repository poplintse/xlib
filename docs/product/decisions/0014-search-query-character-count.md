# Decision 0014：搜索关键词按用户感知字符计数

状态：accepted，用户于 2026-09-14 明确确认。

## Context

两端均限制关键词长度为 2–32，但 Android 使用 UTF-16 单位计数，iOS 使用用户感知字符计数。例如一个 😀 在前者算两个单位，后者算一个字符，会造成同一输入在两端校验结果不同。

## Decision

- 搜索关键词先去掉首尾空白，再按用户感知的字符计算长度，允许 2–32 个字符，包含上下界。
- 用户感知字符按 Unicode 扩展字素簇理解，不按字节、UTF-16 单位或单独码点计数。一个普通汉字、英文字母或构成一个完整 emoji 的序列各算一个字符。
- 内部空格保留并参与查询及长度计数；不因长度校验改变原有不区分大小写、不重叠搜索规则。
- 不足 2 个或超过 32 个字符时提示长度要求，不执行该查询，不静默截断输入后搜索。

## Reason

用户认可按实际感知的字符统一长度校验，使相同输入不会因客户端字符串表示方式而被不同对待。

## Consequences

CAP-SEARCH 采用本规则。Android 已使用 ICU 扩展字素簇计数，覆盖首尾空白、组合字符及长度边界；iOS 当前 String.count 方向一致，但完整搜索流程仍需验证。当前状态见能力矩阵。

验收示例：去除首尾空白后的单个 😀 为 1 个字符，应拒绝；😀😀 为 2 个，应允许；2 和 32 个字符通过，33 个拒绝。后续还需覆盖组合附加符、组合 emoji 与首尾空白。

实施与验收状态见 [CURRENT](../../CURRENT.md)。上述字符计数规则不改变原始文件字节 offset 的定位语义。
